# 后端说明

本文档基于当前代码与历史文档整理，描述后端架构、已实现功能与协议约定。

---

## 一、代码结构概览

- **会话**：`SessionState`（可序列化状态）、`PlayerSession`（持有一份 SessionState）、`SessionManager`（内存 Map，可扩展 Redis）。
- **WebSocket**：`GameWebSocketHandler` 收消息后由 `MessageProcessorRegistry` 按 `type` 分发到对应 `MessageProcessor`。
- **消息类型**（`MessageType`）：心跳 1000；登录 1001/1002；移动意图 2002（2001 已废弃）；战斗 3001/3002/3003；道具 4001/4002；场景 5001/5002。
- **地图**：`GameMapService`、`MapWeightSelector`、`MapPathService`、`MapWalkableService`；地图接口 `POST /api/map/{mapId}`。
- **战斗**：`BattleStartProcessor`（3001）、`BattleEngineService`、`DropRollService`；DTO 见 `common.dto.battle`。
- **其他**：`ChestController`/`ChestService`、`ItemController`/`ItemService`、`MonsterController`/`MonsterService`、`AuthController`、`PlayerController` 等。

## 二、已实现功能

### 1. 地图格子事件权重服务端化

- 需求：每个格子「按权重选一个事件」的逻辑在服务端执行，同一地图请求下每格只返回一个事件。
- 实现：`CellEventEntry` DTO；`MapWeightSelector` 对地图 JSON 逐格按权重随机选一个事件（权重为 0 不参与），将 `events` 改为至多一个元素；`GameMapService.getByMapId` 返回前调用 `MapWeightSelector.applyWeightSelectionPerCell(map.getData())`。
- 接口：`POST /api/map/{mapId}` 返回的 `data` 中，每格 `events` 至多一个元素。客户端直接使用 `events[0]`，不再做客户端权重选择。

### 2. 玩家移动 — 意图协议 MOVE_INTENT（2002）

- 原则：前端寻路与动画自主；2002 只传「可走到的终点」（遇怪/宝箱时传相邻格），后端只校验移动合法性并回 SUCCESS 或 400；事件由前端到相邻格后主动发 3001/开箱，后端校验后执行。
- 协议：
  - **C→S**：`{ "type": 2002, "targetX": number, "targetY": number, "mapId": number }`（mapId 可选，首次建议带）
  - **S→C 成功**：`{ "type": 2002, "code": 200, "status": "SUCCESS", "finalX", "finalY", "events": [], "seqId"? }`
  - **S→C 失败**：`{ "type": 2002, "code": 400, "message": "string", "correctPos": { "x", "y" }?, "seqId"? }`
- 后端：`MoveIntentProcessor` 只做「移动到 target」校验；无位置时用 `findEntrance` 设当前格；`MapPathService` 寻路到 target，目标为事件格时路径只到相邻格；不返回 INTERRUPTED 或 action battle/chest。
- 前端：寻路只到相邻格，发 2002 的 target 为路径终点；收到 SUCCESS 后播动画到 finalX/finalY；路径走完后若意图格为怪物/宝箱且相邻，主动发 3001 或开箱请求。

**历史**：原按步校验 PLAYER_MOVE(2001) 已废弃，由 MOVE_INTENT(2002) 替代。

### 3. 用户上下文轻量重构（SessionState + PlayerSession）

- 目标：会话状态与连接解耦，便于后续 Redis / 断线重连，当前仍为内存存储。
- 实现：`SessionState` 含 sessionId、userId、username、gameStatus、mapId、cellX、cellY、loginTime、lastActiveTime、hp、maxHp 等；`PlayerSession` 内部持有一份 `SessionState`，对外保留 getter/setter，提供 `getState()`、`updateState(Consumer<SessionState>)`；`SessionManager` 仍为内存 Map。Processor 通过 session 的 get/set 读写状态，无需改调用方式。
- 扩展：后续可增加 SessionRedisRepository 将状态读写改为 Redis，无需改 Processor/Handler。

### 4. 战斗逻辑后端化（方案 B + 掉落后端随机）

- 目标：战斗计算与掉落随机均在后端完成，Unity 只发 BATTLE_START、收 BATTLE_RESULT 并做表现。
- 实现：`SessionState` 含战斗属性（attack、defence、dodge、accurate、crit、doublehit、reflect、name、icon）；建会话时用默认值填充。`CombatantSnapshot` / `BattleResultDto` / `DropItemDto` 在 `common.dto.battle`；`MonsterService.getById` 单条查库；`BattleEngineService` 负责命中/伤害/暴击/反伤/连击、50 回合上限；`DropRollService` 解析怪物 item 字符串按万分比 roll 掉落。`BattleStartProcessor` 处理 type=3001：校验玩家在 (cellX, cellY) 相邻格、该格确有 monsterId；胜利不更新玩家到怪物格；回包 3003 含 result、cellX、cellY、logs。
- 消息：C→S `{ "type": 3001, "monsterId", "cellX", "cellY" }`；S→C `{ "type": 3003, "code", "result": { "type", "playerCurrentHp", "totalRounds", "drops" }, "cellX", "cellY", "logs" }`。
- Unity：改为发 WS 3001 触发战斗，订阅 3003 用 result.drops + cellX/cellY 做掉落表现，不再本地 ParseAndRoll。

## 三、接口与常量摘要

| 用途       | 说明 |
|------------|------|
| 地图       | `POST /api/map/{mapId}`，返回的 data 每格 events 已按权重至多一个。 |
| 移动意图   | WS type=2002，C→S targetX/targetY/mapId；S→C 仅 SUCCESS(finalX,finalY) 或 400(correctPos)。 |
| 战斗       | WS type=3001 发起，type=3003 回结果（含 result、drops、cellX、cellY、logs）。 |

## 五、历史与废弃说明

- **PLAYER_MOVE(2001)**：原「按步校验」方案已废弃；客户端曾按步发 toX/toY，服务端回 200(cellX,cellY) 或 400。现统一使用 MOVE_INTENT(2002)。
- **第一版移动范围**：不做的项包括位置持久化、ENTER_FLOOR、频率限制、stepId、失败回包纠偏坐标、重连欢迎包权威位置、PLAYER_MOVE 超时重试等；若后续需要再在第二版中补充。
